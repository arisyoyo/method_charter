# merge 模式：合并人工确认的变更

## 输入（三件套，缺一不可）

1. 当前 `method-core.md`
2. **经人工确认的变更内容**——由人从修改会话的产出里提取，不直接喂整段对话
3. 变更理由

第 2 项是过滤污染的最后一道闸。人工没提取过的内容不进 merge，即使它看起来很好。

## 硬规则

- **未受影响的部分逐字保留**：标点、语序、术语写法、表格列序都不动。
- 只改被明确点名的区块；不得顺手「优化」其他段落。
- 不做风格统一、不调格式、不补例子——那是 distill 的事。

这条与 `distill` 的方向相反（distill 允许重组以适配预算），**所以两种模式不能混在一次执行里**。

## 兼容性检查（三项，全过才能出新版本）

### 1. 章节兼容

扫描各章 frontmatter 的 `method-version`（约定：每章 Markdown 头部记 `method-version: 2.1.0`）。

本次变更若使某章不再合规，**列为受影响章节**。这一项才让「全链路可追溯」有落点——否则你只知道主文档变了，不知道哪些正文还写在旧版约束下。

### 2. 术语兼容

- 新增或改名的术语，是否已写进 §3.1 **和** §3.2 禁替代表；
- 旧写法是否仍被允许（不允许就列出受影响的章节）。

### 3. 红线兼容

变更是否触及 §4.1 任何一条。**触及即硬停**，转人工裁决，不产出新版本。

## 版本号

按**契约兼容性**分级，不按修订粒度：

| 判定 | 版本 |
|---|---|
| 破坏既有章节合规（术语改名、删结论、动红线） | `X+1.0.0` |
| 只增不改（新增术语、新增可调整项） | `X.Y+1.0` |
| 编辑性（措辞、错字、补例子） | `X.Y.Z+1` |

理由：下游要回答的问题是「我的章节还有效吗」，不是「改了几个词」。改一个核心构念的名字只有一个词，却足以让全部已写章节失效。

## CHANGELOG（append-only）

```markdown
## v2.1.0 — 2026-11-01
- **类型**：术语级 / 框架级 / 编辑级
- **变更**：<一句话>
- **理由**：<为什么改>
- **来源**：context-clean-20261101.md / 冲突上报 #3
- **兼容性**：影响 §3.2；受影响章节：第 4 章（需重写术语）；其余不受影响
- **人工确认**：<人名> @ 2026-11-01 16:20
```

- **只追加，不改写，不删。** 任何模式都不得修改已有条目。
- 变更史必须独立成文件。放进 `context-clean` 会被下一次 clean 当成过程性内容折叠掉——**历史被清理工具改写，是这套流程里最不该发生的污染**。
- 版本号、日期、来源三项必填；「兼容性」不写「无影响」的空话，要写清排除过程。

## 冲突处理

变更与内核冲突时**不强行合并**。输出冲突分析，不产出新版本：

```text
【合并冲突】
- 冲突点：变更要求把 X 表述为 Y，但 §2.1 的逻辑链第三步是 X
- 路径 A：改内核（框架级，X+1.0.0，全部章节需重查）
- 路径 B：改变更本身，保留内核（编辑级）
- 各自影响：<…>
- 待裁决：<人能一句话回答的问题>
```

## 归档

新版本落盘前，先把旧 `method-core.md` 复制为 `_archive/method-core-v<旧版本>.md`。

- 归档只增不删，不改名、不压缩、不合并。
- **版本号在 frontmatter 里，不在文件名里**——文件名一改，Obsidian 的链接就断，章节里的引用会静默悬空。
